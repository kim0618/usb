# MANUAL-R2 인간 판단 데이터 계약 V1

작성 2026-09-28. **설계 문서다. 화면 배포 0, 운영 코드 수정 0.**

---

## 0. 왜 필요한가

MANUAL-R1의 H2는 정정 후에도 **질문으로는 남는다**:

> 사용자가 LONG과 SHORT를 가르는 정보는 무엇인가?

원장은 이 질문에 답할 수 없다. **진입 가격과 시각은 결과이지 이유가 아니다.**
표본을 1건에서 100건으로 늘려도, 이유가 기록되지 않으면 H2는 그대로 열려 있다.

> **표본 수가 병목이 아니라 라벨이 병목이다.**

---

## 1. 무엇을 기록하나

### 1.1 필수 (없으면 연구 대상 아님)

| 필드 | 타입 | 값 |
|---|---|---|
| `decision_id` | str | UUID. 주문과 1:1 |
| `decided_at_ms` | int | **버튼을 누르기 직전** 클라이언트 시각 |
| `server_received_ms` | int | 서버 수신 시각. 둘의 차이가 지연 |
| `side` | enum | LONG / SHORT |
| `reason_code` | enum | §2 |
| `conviction` | int | 1-5 |

### 1.2 선택 (있으면 가설 검정력이 올라간다)

| 필드 | 타입 | 값 |
|---|---|---|
| `expected_direction_bp` | float? | 기대 이동폭 |
| `expected_horizon_minutes` | float? | 기대 소요 시간 |
| `invalidation_price` | float? | **"여기까지 가면 내가 틀린 것"** |
| `free_note` | str? | 자유 서술. 분류에 쓰지 않는다 |

`invalidation_price`가 선택 중 가장 가치가 높다. 방향 예측과 달리
**반증 가능한 진술**이고, 사후에 기계적으로 채점된다.

### 1.3 자동 부착 (사용자가 입력하지 않음)

| 필드 | 값 |
|---|---|
| `mark_at_decision` | 결정 시각의 mark |
| `spread_at_decision`, `basis_at_decision` | 동일 |
| `tape_snapshot_ts_ms` | 사용된 스냅샷의 시각 |
| `ui_context` | 보고 있던 화면(차트 구간, 선택 레버리지, 프리셋) |
| `origin` | **`USER_MANUAL`** (이 경로 전용) |

## 2. reason_code 어휘 (closed)

| code | 의미 |
|---|---|
| `TREND_CONTINUATION` | 추세가 이어진다고 본다 |
| `REVERSAL_EXHAUSTION` | 한쪽이 소진됐다고 본다 |
| `RANGE_EDGE` | 구간 경계에서 되돌림을 본다 |
| `BREAKOUT` | 구간 이탈이 이어진다고 본다 |
| `PULLBACK_ENTRY` | 추세 중 되돌림에 올라탄다 |
| `LIQUIDATION_CASCADE` | 청산 연쇄를 본다 |
| `FUNDING_SKEW` | funding 쏠림을 본다 |
| `NEWS_EVENT` | 외부 사건 |
| `GUT` | **근거를 말로 못 하겠다** |
| `OTHER` | 위 어디에도 없음. `free_note` 필수 |

| # | 규칙 |
|---|---|
| R1 | **`GUT`은 정당한 값이다.** 이 선택지를 없애면 사용자가 아무거나 고르게 되고, 라벨 전체가 오염된다 |
| R2 | 기본 선택값을 두지 않는다. 미선택 상태에서 주문 불가 |
| R3 | 어휘 확장은 버전 상승(`V2`)으로만. 기존 값의 의미를 바꾸지 않는다 |

## 3. 시점 규칙 (PIT)

| # | 규칙 |
|---|---|
| **P1** | 판단은 **주문 전**에 기록된다. 주문 후 입력 금지 |
| **P2** | 기록 시각 이후의 가격을 보고 쓴 것은 판단이 아니라 회고다 |
| **P3** | 결과를 본 뒤 수정 금지. 수정은 **append-only 개정 레코드**로만 남고, 연구는 **최초 레코드만** 쓴다 |
| **P4** | 자동 부착 필드는 `decided_at_ms` **이전** 스냅샷에서만 가져온다 |

P3가 없으면 "내가 이래서 샀지"가 사후에 조립된다. 그건 데이터가 아니다.

## 4. 누락 처리

| 상황 | 처리 |
|---|---|
| 판단 기록 없는 주문 | `decision_label = MISSING` |
| `reason_code = GUT` | 정상 값. 별도 그룹으로 집계 |
| 사후 입력 시도 | `decision_label = RETROSPECTIVE`. **연구 제외** |

| # | 규칙 |
|---|---|
| M1 | **누락을 추정으로 채우지 않는다.** 가격 움직임에서 reason_code를 역산하면 그것은 내 가설이지 사용자의 이유가 아니다 |
| M2 | MISSING 거래도 **성과에는 포함**된다(USER_MANUAL이면). 라벨이 없을 뿐 거래는 실재한다 |
| M3 | 라벨 기반 분석에서만 제외한다 |

M1이 MANUAL-R1이 저지른 실수의 일반형이다. **모르는 것을 채우지 않는다.**

## 5. 저장

| 항목 | 값 |
|---|---|
| 위치 | 원장과 **별도 파일**(`decisions.jsonl`), 같은 run 디렉터리 |
| 형식 | append-only JSONL, 한 줄 한 레코드 |
| 연결 | `decision_id` ↔ 주문의 `request_id` |
| 보존 | ACCOUNT_RESET이 **삭제하지 않는다** |

**원장에 넣지 않는 이유**: 원장은 회계 무결성 대상이라 테이프 재생과 바이트 일치해야 한다.
판단 기록은 회계가 아니고, 개정 레코드를 허용해야 하며, 스키마가 더 자주 변한다.
둘을 섞으면 판단 스키마 변경이 회계 재생을 깬다.

## 6. 몇 건이 필요한가

**지금 정하지 않는다.** 필요 표본은 검정하려는 가설에 달렸고, 가설은 라벨 분포를 보고야 정해진다.

| # | 규칙 |
|---|---|
| N1 | 수집 중 중간 성과를 보고 규칙을 만들지 않는다 |
| N2 | 판정 기준은 **수집 시작 전에 사전등록**한다(MANUAL-R3) |
| N3 | R2는 **수집만** 한다. 판정하지 않는다 |

D5.5까지 여섯 번의 AUTO 실패에서 반복된 실패 양식이 "보고 나서 기준 정하기"였다.
R2에서 같은 일을 하지 않는다.

## 7. 구현 형태는 사용자 결정

세 가지 모두 이 계약을 만족한다. **내가 먼저 고르지 않는다.**

| 안 | 형태 | 장점 | 단점 |
|---|---|---|---|
| A | 주문 모달에 라벨 입력 | 누락 0, PIT 보장 | UI 작업 필요, 매매 흐름에 마찰 |
| B | 별도 메모 화면 | 구현 가벼움 | 누락 발생, PIT 약함 |
| C | 수집 없이 거래만 축적 | 마찰 0 | **H2를 못 푼다.** 표본만 늘어난다 |

C를 고르면 R3는 성과 검정만 가능하고 방향 규칙화는 불가하다는 점만 기록해 둔다.
