# US-B CRYPTO - D4.1: Two-sided SAFE MAX, 가격 일관성, 운영계좌 정책

> 운영 worktree에서 보존한 과거 기록입니다(2026-10-04 reconciliation). 아래 실측값과 배포 상태는 당시 기록이며 이번 Stage에서 재검증하지 않았습니다. 현재 release의 동작과 정책은 커밋된 코드 및 최신 기능별 계약을 우선합니다. 이 문서의 명령은 이번 Stage에서 실행하지 않았습니다.

## 1. 기존 MAX의 근본 원인

`sizing.max_entry()` 는 **진입만** 시험했다. 진입은 반대쪽 호가를 소모하고,
청산은 그 반대쪽을 소모한다. 두 면은 자주 비대칭이다.

실측(운영, 2026-09-24):

```
포지션 진입   1.082 BTC   ask depth 10.740  -> 체결
전량 청산 시도 1.082 BTC   bid depth  0.157  -> NO_LIQUIDITY
```

엔진은 부분체결을 하지 않는다(`walk_book`: "Partial visible depth is an error, not a fill").
따라서 진입만 보고 고른 크기는 **엔진이 청산을 거부하는 포지션**을 만들 수 있었다.

레버리지 50배였기 때문에 증거금은 넉넉했고, ask는 10배 이상 깊었다.
**아무도 bid를 보고 있지 않았던 것**이 유일한 결함이다.

## 2. SAFE MAX 정의

```
MAX = 이 스냅샷에서 진입과 즉시 전량 청산이 모두 성립하는 최대 격자 수량
```

응답에 `max_definition: "ENTRY_AND_IMMEDIATE_EXIT_ON_THIS_SNAPSHOT"` 으로 실려 나간다.

계산은 여전히 **엔진 probe**다. 공식 역산이 아니다.

```
복제 엔진 A -> 진입 주문            (entry_feasible)
복제 엔진 B (= A 복제) -> 즉시 전량 청산   (exit_feasible)
둘 다 성공해야 valid
```

청산은 **진입과 같은 quote**로 시험한다. 가장 유리한 조건이며, 여기서도 실패하면
1초 뒤에는 더 실패한다.

이분탐색은 여전히 유효하다. 증거금·리스크한도·진입깊이·청산깊이 모두 수량이 커지면
나빠지므로 그 논리곱도 단조다.

25% / HALF / 75% 도 비율로 줄인 뒤 **각각 다시 양면 probe** 한다.
작다고 해서 안전하다고 가정하지 않는다.

### 방향별 결과

양면을 요구하면 왕복이 두 면을 모두 지나므로, **얇은 쪽이 양방향을 똑같이 구속**한다.
그래서 LONG MAX와 SHORT MAX는 깊이만이 제약일 때 수렴한다.
진입/청산 깊이는 방향별로 따로 보고된다(`entry_depth` / `exit_depth`).

실측(운영 재현: bid 0.157 / ask 10.740, 50x):

| | 값 |
|---|---|
| SAFE MAX LONG | 0.157 |
| SAFE MAX SHORT | 0.157 |
| 진입만 봤을 때 | 0.158 이상 (증거금 한도까지) |
| SAFE MAX + 1 step | 진입은 되지만 즉시 청산 실패 |

## 3. 가격 일관성 (preview vs fill)

sizing 응답이 근거를 들고 다닌다.

```
quote_ts_ms, best_bid, best_ask, mark_price,
entry_depth, exit_depth,
fill_price(예상 진입가), exit_fill_price(즉시 청산가),
liquidation_price(강제 청산가), qty, notional, required_total
```

**Mark를 진입 체결가처럼 표시하지 않는다.** 진입은 ask, 청산은 bid에서 체결된다.
화면에도 세 가격을 구분해 표시한다: 예상 진입가 / 즉시 청산가 / 강제 청산가.

### preview는 약속이 아니다

주문 클릭 시 `/api/crypto/order` 가:

1. 최신 quote로 엔진을 갱신하고(`observe(force=True)`)
2. 그 스냅샷에서 **양면 probe를 다시** 돌리고
3. 안전하지 않으면 **409로 거부**하며 현재 안전 최대 수량을 함께 알려준다

`intent=CLOSE` 는 이 게이트를 통과하지 않는다. 청산은 기존 안전 계약을 따른다.

## 4. 호가 신선도

기존 STALE 계약(`feedStatus`, 5초)을 그대로 쓴다. 새 임계값을 만들지 않았다.
LIVE가 아니면 화면이 신규 진입을 막고, quote가 없으면 엔진이 `NO_QUOTE` 로 거부한다.

## 5. 미래 깊이 버퍼: 도입하지 않음 (근거 포함)

운영 테이프 **78,537건**(1Hz, top-5)에서 "현재 깊이 대비 N초 뒤 깊이" 비율 분포를 측정했다.

| horizon | p05 | p25 | median | mean | p95 |
|---|---|---|---|---|---|
| 1s bid | 0.11 | 0.71 | 1.00 | 4.65 | 8.81 |
| 1s ask | 0.11 | 0.72 | 1.00 | 4.54 | 8.34 |
| 5s bid | 0.05 | 0.45 | 1.00 | 7.39 | 18.92 |
| 15s bid | 0.04 | 0.38 | 1.00 | 8.83 | 22.60 |
| 30s bid | 0.04 | 0.37 | 1.01 | 8.97 | 23.42 |
| 60s bid | 0.04 | 0.36 | 1.01 | 8.91 | 23.46 |

- 1초 뒤 **더 얕아질 확률 48.6%**, 절반 미만이 될 확률 17.3%
- 5초 뒤 절반 미만이 될 확률 27.2%

**결론: 고정 비율 버퍼는 방어할 수 없다.**
1초 뒤 5퍼센타일을 덮으려면 가시 깊이의 11%만 써야 하고, 15초면 4%다.
그러고도 5%는 실패한다. 중앙값은 1.00이라 평상시엔 과도하게 보수적이고,
꼬리는 그 보수성으로도 못 막는다. 분포가 극단적으로 무겁다(mean 4.65 vs median 1.00).

그래서 **감으로 50%/70% 같은 숫자를 넣지 않았다.** D4.1이 보장하는 것은
"이 스냅샷에서 즉시 청산 가능"까지이고, 그 이후의 깊이는 **UNKNOWN**이다.

완화 요인: 깊이는 사라지는 만큼 돌아온다(median 1.00, mean 4.65).
운영에서 청산 실패한 1.082 포지션도 1분 뒤 한 번에 청산됐다.
즉 실패는 영구적이지 않고 재시도로 해소되는 성격이다.

## 6. 부분 청산

엔진은 부분체결을 지원하지 않는다(설계상 명시적 선택).
D4.1에서 실행 의미론을 바꾸지 않았다. 부분 청산은 **후속 후보**로 남긴다.

D4.1이 보장하는 최소선은 요구대로:
**SAFE MAX로 만든 신규 포지션은 같은 스냅샷에서 전량 청산 가능**하다.

## 7. Known anomaly: duplicate START (D4)

| 항목 | 값 |
|---|---|
| 현상 | `paper-server-001` 활성 테이프에 `START` 커맨드 중복 기록 |
| 건수 | **5,577건** |
| 발생 범위 | 2026-09-24, 세그먼트 1 회전(약 13:05) 직후 ~ 수정 배포(약 13:34) 사이 |
| 근본 원인 | 회전으로 원래 `START` 가 닫힌 세그먼트로 이동. 세션이 시작시각을 **활성 테이프만 scan** 해서 None을 얻고 "미시작"으로 오판, `start()` 재호출. 엔진은 `RuntimeError: engine already started` 로 거부하지만 테이프 기록은 그 전에 일어나므로, 관측 루프가 매 틱 재시도하며 누적 |
| 영향 | **원장 무영향**(RuntimeError가 원장 기록 전에 발생). 테이프만 오염. 이후 재기동에서 그 START를 재생하다 실패해 서비스 기동 불가 |
| 수정 버전 | 2026-09-24 배포분 |
| 수정 내용 | ① 세션 시작시각 authority = **원장 `RUN_START`** ② 재생 시 **두 번째 이후 START 무시** ③ 레코드 수는 활성+세그먼트 합산 |
| replay 처리 | 첫 `START` 만 적용. 이후 START는 조용히 건너뛴다 |
| 원본 보존 | **원장·테이프 모두 수정하지 않았다.** 5,577건은 그대로 남아 있다 |

> 이 5,577건은 정상 이벤트가 아니다. 테이프를 분석하는 사람이 "런이 5,577번 시작됐다"로
> 읽지 않도록 여기에 기록한다. `RUN_START` 원장 이벤트는 1건뿐이고 그것이 정본이다.

## 8. 운영 Paper 계좌 정책

`paper-server-001` 은 **사용자 실사용 계좌**다.

1. 개발 smoke는 **임시 격리 인스턴스**에서 수행한다(별도 포트·별도 run dir).
2. 운영에서 불가피한 테스트는 최소화한다.
3. **사용자가 open position을 보유 중이면 운영 주문/RESET 테스트 금지.**
4. 기존 거래를 개발 테스트라고 가정하지 않는다.

### cleanup 조건 (전부 충족해야 수행)

- 개발 테스트 이전 사용자 상태가 FLAT이었다
- 해당 거래가 이번 세션에서 생성된 것이 타임스탬프로 명확하다
- 사용자 실제 거래와 혼동되지 않는다

하나라도 불명확하면 **운영 상태를 그대로 둔다.**

### cleanup 절차

CLOSE -> FLAT 확인 -> `ACCOUNT_RESET` -> Equity/Available 정확히 10,000,000원,
미실현 0, 현재 손익 0, feed LIVE 확인.
과거 기록은 삭제하지 않는다. RESET은 자본 경계만 추가한다.

### test provenance (설계만, 미구현)

현재 `reason` 필드는 `MANUAL` / `EMERGENCY` / `LIQUIDATION` / `SIZING_PROBE` 를 쓴다.
smoke 주문에 `SMOKE_TEST` 를 넣으면 analytics `by_origin` 에서 바로 분리된다.
다만 `Trade.origin` 은 기존 체결의 `reason` 을 그대로 읽으므로, 값을 늘리면
기존 분석 카테고리가 변한다. 이번 작업 범위에서는 **설계만 기록하고 넣지 않았다.**
격리 인스턴스를 쓰면 애초에 운영 원장에 들어가지 않으므로 우선순위가 낮다.
