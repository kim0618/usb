# Crypto Paper Memory Pressure Audit V1 (2026-10-12)

Verdict: **B. MEMORY_CAUSE_IDENTIFIED**. The code changes passed parity checks. A memory reduction was **not shown** beyond measurement noise. Nothing was deployed and no service was restarted.

Evidence: `~/usb-crypto-memory-evidence/audit-20261012/`. It holds the raw production samples, CSV, smaps summary, replica series, C1 harness output, replay result, census and harness scripts.

## A. Production baseline (read-only, 15:07 to 15:37 KST, 600 samples at 3 s)

| metric | min | median | max |
|---|---|---|---|
| memory.current (MiB, cap 200) | 184.6 | 195.7 | 200.0 |
| cgroup anon | 155.8 | 170.0 | 178.6 |
| cgroup file (page cache) | 15.3 | 22.1 | 29.7 |
| process swap | 33.7 | 41.0 | 56.1 |
| RSS / PSS | 167.6 / 157.4 | 181.3 / 171.4 | 190.0 / 180.0 |
| host MemAvailable | 158 | 203 | 227 |

- **The process's anonymous memory (median anon + swap) is about 210 MiB, which is above MemoryMax.** The cgroup holds it at the cap by swapping out about 40 MiB and squeezing its own page cache.
- Threads stayed at 16 and fds at 39 to 45. CPU was 9.4% of the single vCPU. PID 1669431 and NRestarts 0 were unchanged throughout.

## B. memory.events

- During the window, `max` rose 2797 → 3615 (about 27/min, in bursts). `high`, `oom` and `oom_kill` stayed at 0. By 16:40 it had reached 5105.
- These events are reclaim at the limit, not kills. At each event the kernel drops page cache or swaps anonymous pages. The risk is latency (cgroup PSI avg10 reached 34) and the swap I/O that hits the host.

## C. C1 memory

- `C1Runtime.tick()` runs every 20 s. Each tick re-downloads 33 days: about 48 kline pages, 48 Binance spot pages, 48 OI pages and funding, roughly 150 requests. The tick takes about 30 s, so one cycle is about 50 s. Each tick then builds a new 47,520-row grid next to the old one.
- Isolated harness, C1 alone: imports 28 MB → after bootstrap 74 MB → after 12 ticks 92 MB (RSS).
- With tracemalloc, about 25 MB of objects stay alive after a tick (the grid is about 11 MB). Each tick allocates about 33 MB more on top of that, which is freed once the tick ends.
- `gc.collect()` changed nothing. `malloc_trim(0)` released about 25 MB. So RSS is several times the live object size because memory the allocator keeps after freeing is not returned to the OS.

## D. Chart cache

- 48 entries, TTL 15 s. **Expired entries were never removed.** They left only when 48 newer keys pushed them out.
- Production uses only about 10 to 15 distinct keys, mostly `1m×64` and `1m×3`. So every large seed that was ever requested (2880 bars, about 1.1 to 1.5 MB each) and every `before_ms` page stayed resident for the life of the process.
- Census (tracemalloc, chart sweep workload): 48 entries = 25.3 MB of live objects.

## E. 15 s candles and dedup

- `SEEN_IDS = 50_000` is a bounded deque+set, so it cannot grow without limit. Measured at about 6.1 MB per book when full.
- BTC runs at about 6 trades/s, so its book fills in about 2.3 hours. ETH and SOL keep their book once opened; only the HOT book is retired.
- Duplicates seen: 0. A duplicate of a trade in an already-finalized bucket is rejected as LATE anyway. Shrinking the window would change the telemetry counters, so it is a P2 candidate and was not implemented.

## F. HOT lifecycle

When the HOT symbol is replaced, the following all run: `retire_trade_feed` stops and forgets the feed, `hot_chart_history.forget` drops its cache pages, the session moves to `retired`, and wallet membership is removed. No leftover per-symbol state was found apart from the bounded objects above.

## G. Allocator and fragmentation

- Production smaps: main heap 35 MB, about 86 MB (RSS+swap) in glibc thread arenas (64 MB-aligned, 6 to 7 of them), and about 85 MB in pymalloc arenas (1 MB mmaps). Live Python objects measured about 70 MB in the replica census, against about 140 to 160 MB RSS.
- `MALLOC_ARENA_MAX=2`:
  - Pair 1 (A vs B): steady 163 → 143 and peak 177 → 147.
  - Pair 2 (V0 vs V1, run at the same time): 135 → 141, and V2 vs V3: 160 → 143.
  - **The effect varies between runs.** CPU and p50/p95 latency were the same. It was not applied in production.

## I. Root cause ranking

1. **The footprint is larger than the cap.** About 210 MiB of anonymous memory against a 200 MiB cap, so reclaim never stops. The replica, which has no LIVE stack and only 20 minutes of uptime, sits at 135 to 170 MB. The remaining 40 to 70 MB comes from the LIVE path (user stream, mirror, reconcile) and long uptime. **This part was not measured** because production must not be instrumented.
2. Allocator retention: RSS is roughly twice the live objects. The C1 bootstrap and tick transients (about 33 MB per tick) set the high-water mark.
3. The chart cache keeps expired pages, about 5 to 25 MB.
4. The 15 s dedup uses about 6 MB per open book.

## K. Chosen fix (committed, not deployed)

- **A** `c1/incremental.py` (new), plus changes to `c1/runtime.py` and `c1/sources.py`:
  - Keeps the raw series. Each tick re-reads only a 3-hour tail and any gaps, then splices in rows rebuilt by `build_grid` (the head and the suffix). The contract arithmetic is not touched.
  - A rotating audit re-reads 1000 minutes of every series per tick. If anything differs, the next tick does a full refresh.
  - It also falls back to a full refresh on the first run, if the start moves back, after a pause over 6 hours, or when there are more than 8 gap ranges.
- **B** `terminal/chart_history.py`, `hot_coins/market.py`: expired pages are dropped on access.

## L. Parity

- `tests/crypto/test_c1_incremental.py`, 7 tests. A synthetic venue (late bars, bars hours late, permanent gaps, spot/OI gaps, signals firing, a long pause, a venue revision, restart) is ticked through both paths. All 9 grid series are compared bit for bit on every tick, along with funding, armed/cursor, the last evaluation, and the signals/shadow/c1x ledgers.
- **Real-data replay:** 36 days recorded from public endpoints, 24 hours replayed (2 h at 20 s ticks + 22 h at 60 s), 1,680 ticks.
  - The grid matched on every tick.
  - All 4,320 evaluated bars were identical.
  - Signals: 0 on both sides; every real bar was OFF. Signal paths are covered by the synthetic test.
  - Rows read: 175.8 M → 1.66 M.
- Known difference: a venue revision of a bar older than 3 hours shows up immediately under the full refresh, and only after the audit reaches that slice (≤ 48 ticks) under the incremental path. Real data has 0 gaps and 0 revisions (36-day sample).

## T. Final verdict

**B. MEMORY_CAUSE_IDENTIFIED.**
- Cause: the anonymous footprint is larger than the cap, and allocator retention after transient churn (C1 33-day reload, chart pages) keeps it there.
- The fixes keep C1 results identical (parity PASS) and cut network and CPU. **The 130 to 150 MB target was not met in this audit.**
