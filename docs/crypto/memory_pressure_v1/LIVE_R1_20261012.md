# Crypto Paper LIVE Memory R1: Read-Path Allocation Audit (2026-10-12)

Verdict: **A. LIVE_PATH_CAUSE_NOT_CONFIRMED.** No code was changed. Nothing in production was restarted, signalled or attached to. No order was sent.

Evidence: `~/usb-crypto-memory-evidence/live-r1-20261012/`, which holds the production mirror copy, the public exchangeInfo payload, the harness, `runs.jsonl` (cold process) and `runs_warm.jsonl` (pre-fragmented 158 MB process).

## 0. Scope check

- These 12 files are byte-identical (sha256) between the deployed copy and local `main`: `live/{mirror,leverage,account,adapter,filters,rest,stream,exit_guard,performance}.py`, `hot_coins/{scanner,service}.py` and `terminal/live_routes.py`.
- Production at 17:20 KST: MemoryCurrent 199.7/200 MiB, VmRSS 183 MB, VmSwap 43 MB, VmHWM 197 MB. PID 1669431, NRestarts 0.
- Production access was read-only: `systemctl show`, `/proc/PID/status`, sha256 of the deployed files, and one `scp` of the mirror file.

## 1. Mirror read path

**The 9.2 MB mirror is not re-read on a timer.** Every reader is listed below.

| reader | when | how | measured (warm process) |
|---|---|---|---|
| `LiveMirror.__init__` line count | once at startup | streamed | +0.1 MB, 9 ms |
| `restriction_from_mirror` (bootstrap) | once per symbol, the first time the symbol is built | streamed, one line at a time | 3 symbols: +0.2 MB HWM, 0.33 s CPU |
| `account_scope_from_mirror` | each `GET /binance/leverage`. The UI calls it on LIVE enter, on symbol change and after a leverage change, not on the poll | streamed | +0.2 MB HWM, 0.08 s CPU |
| `LiveMirror.recent()` file fallback | `GET /binance/events` while the in-memory tail is empty (only right after a restart, before the first snapshot) | `read_text()` of the whole file plus `splitlines()` | **+26 MB HWM**, 7.5 MB retained |

- The UI never calls `/binance/events`. `liveApi.events` is defined but no component uses it.
- The only full-file read is therefore latent and does not run in normal use.
- Candidates A to D (offset tail, side index, bounded window, streaming parse): the scans that actually run are already streaming parses, so the possible saving is about 0.2 MB.

What the file is made of:

- 15,345 of its 16,449 lines (8.93 MB, 97%) are `LIVE_RECONCILE`, and 12,930 of those have reason `FORCED`.
- Those come from the UI's 5 s sizing poll, which calls `get_sizing()` → `snapshot(force=True)`. The median gap between FORCED lines is 4.9 s.
- The file grows on the days the LIVE screen is open (8,210 lines on 10/04). This is disk growth, not memory.

## 2. Account refresh path

- Server side, nothing polls the account on its own:
  - ExitGuard reads only while ARMED. It is ERROR/off.
  - The user stream only raises dirty flags.
  - Every account read is caused by an open LIVE browser screen.
- An open screen polls:
  - `/account` every 2 s. This reads the cached snapshot and does the fast tier (mark, book, positionRisk) when it is more than 1 s old, or a full read after the 30 s TTL.
  - `/sizing`, `/position`, `/exit-guard` and `/performance` every 5 s. Sizing forces a full 8-call read: exchangeInfo (1 h TTL), premiumIndex, bookTicker, positionSide/dual, v3/account, v3/positionRisk, symbolConfig, commissionRate, plus leverageBracket (1 h TTL).
- The LIVE routes are `async def` with no `to_thread`, so these reads allocate on the event-loop thread (main arena).
- Today, by hour: 238 RECONCILE at 09h (the preview incident), 120 at 15h, 82 at 16h. LIVE use is intermittent.

Where each field goes:

| field | source endpoint | consumers |
|---|---|---|
| balance / availableBalance / margin | `v3/account` | `/account` view, Safe MAX via sizing `available`, ExitGuard (card), performance |
| position | `v3/positionRisk` (fast + full) | `/account`, `/position` card, preview `held_notional`, sizing, ExitGuard match |
| leverage / margin type | `symbolConfig` | preview, sizing, card, `/leverage` current |
| brackets | `leverageBracket` (1 h TTL) | preview, sizing |
| filters | `exchangeInfo` (1 h TTL) | preview, sizing, order qty, `base_asset` |
| fee | `commissionRate` | preview, sizing, card |
| position mode | `positionSide/dual` | blocker (hedge mode) |
| open orders | not read on the poll | none |

**One simulated LIVE screen-hour** (720 forced full reads + 1,800 account polls = 5,762 requests, 720 mirror appends, gzip-encoded payloads decoded by the real `httpx`): **+0.5 MB HWM and +0.5 MB retained** after the first read. CPU was 3.6 s per hour on a mock transport.

- So splitting endpoints, replacing reads with stream fields, or adding a TTL would save about 0.5 MB.
- No parity design is needed because nothing is changed.
- Cadence was not touched.

## 3. exchangeInfo path

- `GET /fapi/v1/exchangeInfo?symbol=BTCUSDT` **ignores `symbol`**. Fetched 2026-10-12: 928 symbols, 1,152,481 bytes decoded (51.5 KB gzip on the wire), the same body with or without the parameter.
- Callers:
  - each symbol's `AccountReader.filters()`: 1 h TTL, one reader per symbol built lazily, so up to 4 decodes per hour with BTC, ETH, SOL and HOT open;
  - `HotScanner._symbols()`: 1 h TTL, only when the HOT scan button is pressed. It **keeps all 928 rows** until the next refresh.
- Rule changes are still detected: each reader refetches after its TTL, and `force=True` exists.

| workload | cold process HWM / retained | warm process HWM / retained |
|---|---|---|
| 1 decode + `SymbolFilters` | +8.0 / +3.0 MB | **+3.9 / +2.0 MB** |
| 4 symbols (4 decodes) | +14.3 / +11.3 MB | **+7.4 / +0.6 MB** |
| 10 decodes back to back | +21.1 / +5.0 MB | +13.9 / +0.4 MB |
| HOT scanner retained rows | +8.0 / +4.9 MB | +4.0 / +2.0 MB |

Possible fixes and their measured effect:

- One shared decode per hour for all symbols: about 3.5 MB of hourly peak saved, and only while several symbols are open.
- Keeping only the slimmed rows the HOT scanner needs: about 2 MB steady.

## 5. Contribution summary ("which path, how many MB")

| path | warm HWM contribution | frequency in production | fix saving |
|---|---|---|---|
| mirror scans (bootstrap, `/leverage`) | 0.2 MB | per symbol build and per LIVE enter | ≈0 |
| mirror `recent()` fallback | 26 MB | ≈ never (UI does not call it) | 26 MB latent, 0 in practice |
| 5 s account full read | 0.5 MB per screen-hour | while LIVE screen open | ≈0.5 MB |
| exchangeInfo per-symbol decodes | 3.9 to 7.4 MB peak | ≤ 4 per hour while LIVE open | ≈3.5 MB peak |
| HOT scanner retained exchangeInfo | 2.0 MB steady | after the first HOT scan | ≈2 MB |

- In total, the LIVE read paths account for **about 4 to 8 MB of transient peak and about 2 to 3 MB retained**.
- That does not explain the about 74 MiB production-only footprint, and it is below the ±10 MB replica noise floor from the previous audit.

## 6. Parity and safety

- No fix was selected, so there is no behaviour change to prove parity for.
- Baseline: `backend/tests/crypto/test_binance_live*.py` passes 277 of 277 when run from the repo root. Run from `backend/`, one test fails on a relative path.
- No order, CLOSE, leverage mutation, AUTO, ExitGuard or MemoryMax change was made, and there was no restart, signal or attach.
- One stray remote `find /` (started by this audit to locate the mirror) was stopped by its exact PID after 131 s.

## 7. Fix selection

None implemented. The minimum condition is a significant reduction in steady RSS or HWM:

- The largest real-use saving is exchangeInfo (about 3.5 MB peak, hourly, multi-symbol only) plus the HOT rows (about 2 MB). Both are under the noise floor.
- The 26 MB `recent()` spike is real but untriggered.

If any of these is revisited later, as a cleanup rather than as the memory fix:

1. Make `recent()` read the tail with a bounded `deque(maxlen=limit)` over a streamed file. The output is the same list.
2. Decode exchangeInfo once per TTL and share it across readers. The response is symbol-independent.
3. Have the HOT scanner keep only the fields `classify_universe` and `instrument_from_exchange_info` read.

## 8. Final verdict

**A. LIVE_PATH_CAUSE_NOT_CONFIRMED.**

- The three suspects (mirror re-read, 5 s account read, exchangeInfo reprocessing) together add about 4 to 8 MB of transient peak in a production-sized heap.
- The mirror is not re-read on a timer.
- The 5 s path is about 0.5 MB.
- The production-only gap is still unexplained. The remaining suspects are allocator history over a long uptime and the thread arenas of `to_thread` workers (C1, chart, HOT), not the LIVE read path.
- Production apply: none.
