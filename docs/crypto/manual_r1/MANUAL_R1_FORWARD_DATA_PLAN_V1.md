# MANUAL-R1 Forward Data 수집 계획 V1

작성 2026-09-28. **제안 문서다. 이번 단계에서 운영 구현 0.** 실제 구현은 별도 승인 뒤에만.

---

## 0. 왜 필요한가

MANUAL-R1은 두 가지를 확인했다.

1. 현재 원장으로는 **성과가 검증되지 않는다**(-413.86 USDT, 17건).
2. 설령 검증됐더라도 **규칙으로 옮길 수 없다**: LONG과 SHORT의 진입 시점이 구별되지 않아
   (17/17건이 1시간 범위 하단), **방향을 가르는 정보가 기록에 없다.**

두 번째가 forward 수집의 진짜 이유다. 표본을 늘리는 것만으로는 2번이 풀리지 않는다.
**무엇을 보고 방향을 정했는지**가 기록돼야 한다.

---

## 1. 현재 기록되는 것과 빠진 것

| 항목 | 현재 | 필요 |
|---|---|---|
| 진입 시각·방향·수량·레버리지 | **있음** (ledger) | - |
| 체결가·수수료·funding | **있음** | - |
| 진입 전 호가·mark·index (1초 해상도) | **있음** (input tape) | - |
| **tape 보존 기간** | 세그먼트 회전, 161MB 누적 | 연구용 장기 보존 규칙 |
| **15초봉 화면 상태** | **없음** | 사용자가 실제로 본 것 |
| **사용자의 진입 이유** | **없음** | 방향 결정의 유일한 단서 |
| 진입 시점의 미결 주문·취소 | 부분(ORDER_REJECTED만) | 망설임의 흔적 |

**tape은 이미 충분하다.** 1초 해상도로 진입 전 1시간이 전부 남아 있다.
빠진 것은 **시장 데이터가 아니라 사람 쪽 데이터**다.

## 2. 제안 스키마 - `manual_entry_snapshot`

수동 주문이 체결되는 순간 연구용으로 한 줄 기록한다.

```json
{
  "schema": "MANUAL_ENTRY_SNAPSHOT_V1",
  "entry_ts_ms": 1790409133083,
  "request_id": "...",
  "side": "SHORT",
  "qty": "0.921",
  "leverage": "10",

  "reason_code": "TOO_FAR_UP",
  "reason_free_text": null,
  "confidence": null,

  "market": {
    "best_bid": "84037.9", "best_ask": "84038.3", "mark": "84038.2",
    "index": "84072.1", "funding_rate": "0.0001",
    "next_funding_time_ms": 1790424000000,
    "spread_bp": 0.05, "basis_bp": -4.01
  },

  "candles_15s_before": [ { "ts_ms": ..., "o": "...", "h": "...", "l": "...", "c": "...", "v": "..." } ],
  "candles_1m_before":  [ { "ts_ms": ..., "o": "...", "h": "...", "l": "...", "c": "...", "v": "..." } ],

  "position_state": { "was_flat": true, "prior_exit_ts_ms": ..., "seconds_since_prior_exit": ... },
  "account_state": { "equity": "...", "available_margin": "...", "segment": 3 },

  "context_source": "paper terminal feed",
  "book_synthetic": false
}
```

| 블록 | 이유 |
|---|---|
| `reason_code` | **가장 중요하다.** 방향 결정 정보의 유일한 출처 |
| `candles_15s_before` | 사용자가 실제로 보는 화면(V2.6에서 추가된 15초봉). 진입 전 40봉 = 10분 |
| `candles_1m_before` | 더 긴 맥락. 진입 전 60봉 = 1시간 |
| `market` | 호가·basis·funding. 지금도 tape에 있으나 진입 줄에 같이 있으면 정렬 비용이 사라진다 |
| `position_state` | 직전 청산 후 경과 시간. 연속 진입·보복 진입을 볼 수 있다 |
| `account_state` | 리셋 구간 구분 |

**candles는 만들어내지 않는다.** 15초봉은 V2.6 이후 기간에만 존재하므로, 그 이전 진입에는
`null`을 넣고 없는 데이터를 합성하지 않는다.

## 3. `reason_code` 후보 (UI 구현은 승인 뒤)

진입 버튼 옆에 선택형 한 줄. **필수가 아니라 선택**이어야 한다. 강제하면 아무 값이나 눌린다.

| 코드 | 의미 |
|---|---|
| `TOO_FAR_UP` | 너무 많이 올랐다 |
| `TOO_FAR_DOWN` | 너무 많이 내렸다 |
| `HIGH_BLOCKED` | 고점에서 막혔다 |
| `LOW_HELD` | 저점에서 버텼다 |
| `WEAK_BOUNCE` | 반등이 약하다 |
| `TREND_TURN` | 추세가 바뀌는 느낌 |
| `FOLLOW_MOVE` | 움직임을 따라간다 |
| `OTHER` | 기타 (자유 입력) |

**이 목록은 제안이고 사용자가 고쳐야 한다.** 실제로 머릿속에서 쓰는 말이 아니면 라벨이
무의미해진다. `TOO_FAR_UP`과 `FOLLOW_MOVE`를 구분하는 것이 특히 중요하다 -
MANUAL-R1은 사용자가 후자를 하고 있다고 보는데 설명은 전자였다.

## 4. 수집 규모 목표

| 항목 | 현재 | R2 목표 |
|---|---|---|
| 완료 거래 | 17 | **60 이상** |
| SHORT 완료 거래 | 6 | **30 이상** |
| `reason_code`가 붙은 진입 | 0 | **전체의 80% 이상** |
| 리셋 없는 연속 구간 | 최장 1건 | **30건 이상** |

**60건은 통계의 시작점이지 충분함이 아니다.** D5.4/D5.5가 200건대에서도 확정을 피했다.
다만 방향 라벨이 붙으면 훨씬 적은 표본으로도 "같은 자리에서 무엇이 방향을 갈랐나"를 볼 수 있다.

## 5. 구현 원칙 (승인 시)

| # | 규칙 |
|---|---|
| I1 | **연구 기록은 거래 경로를 막지 않는다.** 기록 실패가 주문 실패가 되면 안 된다 |
| I2 | 별도 파일에 append. 기존 `ledger.jsonl`·`input.jsonl` **스키마 변경 금지** |
| I3 | 15초봉은 메모리 링(4시간)에서 읽으므로 재시작 후 잠시 비어 있을 수 있다. 그때는 `null` |
| I4 | 운영 계좌·원장에 아무 영향 없음. 읽기만 |
| I5 | 배포는 V2.7과 같은 절차(롤백본 먼저, 소스 롤백은 frontend 트리 **밖**) |
| I6 | `reason_code`는 **선택 입력**. 미입력 시 `null`이고 주문은 정상 진행 |

## 7. 대안 - 구현 없이 할 수 있는 것

운영을 건드리지 않고도 표본은 쌓인다.

| 방법 | 얻는 것 | 잃는 것 |
|---|---|---|
| **그냥 계속 매매한다** | 완료 거래 수, tape 맥락 | 방향 이유(가장 중요한 것) |
| 매매할 때 **사용자가 따로 메모** | 방향 이유 | 손이 많이 가고 누락되기 쉽다 |
| tape 세그먼트를 주기적으로 로컬 보존 | 장기 맥락 | 없음(읽기 전용) |

**두 번째가 구현 없이 H2를 푸는 유일한 방법이다.** 진입할 때마다 코드 한 단어
(`TOO_FAR_UP` 같은)와 시각만 남겨도 다음 분석이 가능해진다.
